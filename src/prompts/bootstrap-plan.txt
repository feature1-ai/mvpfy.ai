Rules for tenancy:

• Work out how this product decides WHICH CUSTOMER a request belongs to, because on
  localhost there is no subdomain and usually no answer — the app then serves nothing, or an
  error about an unknown workspace, or a default that behaves unlike any real customer.
  Look for subdomain parsing, a middleware reading the Host header, a path prefix, or a
  tenant/workspace/org header.
• "mode": "none" when every user shares one instance. Most products. Say so plainly rather
  than inventing tenancy that is not there.
• "local" is what to BE here: for "host" a hostname the proxy can send and the app resolves
  (demo.localhost is the usual shape); for "path" the first segment; for "header" the value.
  Pick one that matches the demo customer you plan to seed, so the login you give the
  product manager lands in the workspace they can see.
• Keep it to letters, numbers, dots, dashes and underscores. It is written into generated
  configuration and sent to a real server.

Rules for the components list:

• List every part of the product this workspace is supposed to run, and every part the code
  plainly EXPECTS to exist. One entry each; a repository holding two deployables is two
  entries.
• "state": "found" when the code for it is here — say which directory in "repo".
  "state": "missing" when the code refers to it and it is NOT in this workspace: an env var
  pointing at an admin dashboard, a fetch to an API in another repository, a mobile client
  that talks to this backend, an OAuth callback into a product that is not here.
• "evidence" is the reason you believe it, quoted small and exactly — "VITE_ADMIN_URL in
  .env.example", "src/api.ts posts to https://admin.acme.com". A guess with no line behind
  it is not a component; leave it out.
• A missing component is the most useful thing in this file. Setting up without one produces
  an app that half works with nothing on screen saying which half — so look for them
  deliberately rather than describing only what is in front of you.
• Never mark something missing just because it is a third-party service (Stripe, S3, an
  email provider). Those are stand-ins you plan as tasks, not parts of the product.
• Do not decide what to do about a missing component. The product manager answers that, and
  the next run reads their answer.

Rules for the task list:

• 4 to 8 tasks. One per real decision — not one per file you touch.
• Titles and details are for a product manager, NOT an engineer. They are about their
  product, not about Docker. No jargon, no tool names unless the PM would recognise them.
    good: "Give your app a database" / "Your app expects a payments service that isn't in
           this code — I'll serve realistic fake responses so checkout works offline"
    good: "Create a demo login" / "Your sign-in emails a code, so I'll add a local inbox you
           can read it from"
    bad:  "Write multi-stage Dockerfile with layer caching"
• Be honest and specific about what is a STAND-IN rather than the real thing — that is the
  single most useful thing this list tells the PM.
• "files" lists the workspace-relative files that task will produce (for example
  docker-compose.mvpfy.yml, mvpfy.yml, .env). mvpfy checks these on disk to confirm the task
  really happened, so only list files you will actually write, and list them accurately.
  Leave "files" as [] for a task that produces nothing to check (e.g. reading the code).
• Every task starts in lane "todo". Never write any other lane in this step.
• Do NOT add a final "app is running" or "verify" task — mvpfy adds that one itself, and the
  product manager is the one who closes it.

Write the file and stop. The next run does the actual work.
