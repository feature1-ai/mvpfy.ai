You are helping a non-technical product manager see this application running locally.

GOAL: after your changes, running `docker compose -f docker-compose.mvpfy.yml up -d` from the
repo root must bring up EVERYTHING the app needs, and the main app must be reachable in a
browser at http://localhost:{basePort} (this port has been verified free on this machine).

Workspace: {repoPath}

The workspace root is either a single application repo, or a folder that contains MULTIPLE
repos (e.g. frontend, backend, services), each cloned into its own subdirectory. Treat every
repo in the workspace as part of one product: they must build, connect, and run together.

Follow these steps:

1. Analyze every repo in the workspace. Work out what each one is (frontend, backend,
   full-stack, monorepo) and list every service the product depends on: backend API,
   database, cache, queue, mail, object storage, third-party APIs. Work out how the repos
   talk to each other (API base URLs, env vars) and wire them accordingly.

2. If mvpfy-answers.md exists in the repo root, read it first — it contains the product
   manager's answers to questions from a previous run. Honor those answers.

3. For every dependent service that is missing, make it available locally:
   • Infrastructure (database, cache, queue, mail, object storage): add it as a service in
     docker-compose.mvpfy.yml using official open-source images with safe local defaults —
     e.g. postgres, mysql, redis, rabbitmq, minio (S3), mailhog (SMTP).
   • Backend/API whose code is NOT in this repo: if the answers file points to a repo or a
     reachable URL, use that. Otherwise generate a minimal mock service under
     mvpfy/services/<name>/ inside the repo root (json-server, or a small Node/Express app —
     open-source tooling only) that serves the endpoints this app calls with realistic sample
     data, and wire the app to it via environment variables.
   • Third-party APIs that cannot run locally (payments, external SaaS): point the app at a
     mock as above, or disable the feature via env flags with a note in mvpfy-run.md.

4. Mobile repos (Flutter / React Native) — the PM still needs to SEE the app:
   • Flutter (pubspec.yaml with a flutter dependency): prefer the WEB build for local
     preview. Build it in Docker with an open-source Flutter image (e.g.
     cirruslabs/flutter) via `flutter build web` and serve the output with nginx on port
     {basePort}. Note in mvpfy-run.md that this is a web preview of a mobile app.
   • React Native with Expo (or react-native-web): serve the web export on {basePort} when
     the app supports web. ALSO run the Expo/Metro dev server as a compose service and
     record its URL in mvpfy.yml as:
       mobile:
         kind: expo
         expo_url: exp://<LAN-IP-of-this-machine>:8081
         note: <one line telling the PM what to expect>
     (detect the machine's LAN IP; the app shows this as a QR code the PM scans with the
     free Expo Go app to see the real native app on their phone).
   • Bare React Native / Flutter with no web support: run Metro and every backend service
     anyway, add the `mobile:` block with a note explaining that the native UI needs a
     simulator and which command to use — never fake a preview.
   • Mobile apps must point their API base URL at the machine's LAN IP (not localhost or a
     Docker hostname) so a real phone can reach the local backend.

5. Only if you are genuinely blocked — for example you need the URL of the real backend repo,
   or a credential that cannot be defaulted — write a short numbered list of questions to
   mvpfy-questions.md in the repo root and stop there. Never guess or fabricate secrets.
   If you were able to proceed, delete any stale mvpfy-questions.md.

6. Generate these files in the WORKSPACE ROOT:
   • mvpfy.yml — app name, main service, host port, list of all services, health-check URL.
     If the app has authentication, seed a working demo account and record it in a
     `demo_login:` block (url, email/username, password, and how to get the OTP if login
     needs one — e.g. "read the code at the mailhog URL"). Add a `demo_credentials:` list
     for any extra logins (admin dashboards, secondary roles). These must be local-only
     demo values, never real secrets — the app displays them to the product manager.
   • Dockerfile — inside any repo that has none (one per repo that needs it)
   • docker-compose.mvpfy.yml — one compose file that runs every repo's app plus every
     dependent service from step 3; build contexts point at the right subdirectory
   • .env.mvpfy.example — safe local defaults for every environment variable the product needs
   • .env — the LIVE env file, same keys as the example with every value filled in with its
     working local default (never a placeholder like "changeme" — the stack must boot with
     exactly these values). Wire every service to it (env_file: .env or ${VAR}
     interpolation in the compose file) so the values actually reach the containers — the
     product manager edits this file from the app and expects changes to take effect on
     restart. Optional third-party keys stay as empty values with the feature disabled.
   • mvpfy-summary.md — 5–8 plain-language lines FOR THE PRODUCT MANAGER: what will run,
     the ports, what was mocked or disabled, roughly how long the first build takes, and a
     closing line confirming everything runs locally on their machine. No jargon — they
     read this instead of the Dockerfile.

Rules:
• The main user-facing app must be exposed on host port {basePort}; give other repos' apps
  their own nearby host ports and record them all in mvpfy.yml and mvpfy-run.md.
• Use a named Docker volume for each database so data persists between restarts.
• Initialize fresh databases from the committed schema file when the framework keeps one
  (Rails db/schema.rb or structure.sql → `rails db:schema:load`, Django, Prisma, …), NOT by
  replaying the full migration history — old migration chains are often broken when run from
  scratch. Guard the load so it only runs on an empty database and never wipes data on a
  container restart, and never auto-run pending migrations at startup.
• Reuse the existing Dockerfile/docker-compose.yml if present.
• Use official base images only.
• Keep images SLIM — builds run on a PM's laptop and network. Do not apt-get compiler
  toolchains or large packages (chromium, g++, libvips-dev, …) unless the app provably
  needs them: modern npm packages ship prebuilt binaries (sharp needs no libvips build,
  puppeteer downloads its own chromium). If a truly heavy native dependency is required,
  pick an official base image that already contains it instead of installing via apt.
• Do not overwrite existing files without creating a .bak backup first.
• Everything you generate must live under the repo root (use mvpfy/ for mock services).

Finish by writing mvpfy-run.md: which services run, their ports, how the product manager can
tell the app is working (what they should see at http://localhost:{basePort}), and any manual
steps that remain.
