Follow these steps:

3. For every dependent service that is missing, make it available locally:

     e.g. postgres, mysql, redis, rabbitmq, minio (S3), mailhog (SMTP).

     mvpfy/services/<name>/ inside the repo root (json-server, or a small Node/Express app —
     open-source tooling only) that serves the endpoints this app calls with realistic sample
     data, and wire the app to it via environment variables.
   • Third-party APIs that cannot run locally (payments, external SaaS): point the app at a
     mock as above, or disable the feature via env flags with a note in mvpfy-run.md.

4. Mobile repos (Flutter / React Native) — the PM still needs to SEE the app:

     cirruslabs/flutter) via `flutter build web` and serve the output with nginx on port

Rules:
• The main user-facing app must be exposed on host port {basePort}; give other repos' apps
  their own nearby host ports and record them all in mvpfy.yml and mvpfy-run.md.
• In mvpfy.yml the main app's `host_port` and the port in its `url` must be identical and
  must be the port actually published in docker-compose.mvpfy.yml. If {basePort} truly
  cannot be used, pick the nearest free port and write THAT consistently everywhere — the
  app reads mvpfy.yml to know where to find the running product.
• Run the app in DEVELOPMENT mode: bind-mount the repository source into the container and
  start it with the framework's own file watcher, so editing the code changes the running
  app without rebuilding the image. Use what the stack already provides — nodemon, `next
  dev`, `vite`, `nest start --watch` for Node; `uvicorn --reload`, `flask --debug`,
  `manage.py runserver` for Python; `rails server` for Rails; `air` for Go. Keep installed
  dependencies inside the image by mounting an anonymous volume over node_modules/ (or the
  virtualenv) so the host checkout cannot shadow them. This matters beyond convenience: the
  product manager tests whatever is checked out, and mvpfy implements each story on its own
  branch, so without a watcher they would be reviewing the previous build.
• Say plainly in mvpfy-run.md which changes appear on their own and which need a restart —
  new dependencies, changed env vars and database migrations always need one.
• Use a named Docker volume for each database so data persists between restarts.
• Seed the demo account as part of the stack STARTING UP — an init script, an entrypoint
  step, or its own compose service — never as a command you run once while setting things
  up. mvpfy runs nothing after `docker compose up`, so a one-off seed exists only in the
  database volume that happened to be there at the time: delete that volume, or the images,
  and the product manager is shown a login that opens nothing.
  Take its email and password from the env file — add them there and to
  .env.mvpfy.example as MVPFY_DEMO_EMAIL and MVPFY_DEMO_PASSWORD — and have the seed read
  them from there, so the env, mvpfy.yml and the account itself cannot drift apart. Make it
  idempotent: create the account when it is absent, leave it untouched when it is already
  there, so it survives every restart and rebuild. Seed any sample data the product manager
  needs to see the product working the same way, and never overwrite data that is there.
• Initialize fresh databases from the committed schema file when the framework keeps one
  (Rails db/schema.rb or structure.sql → `rails db:schema:load`, Django, Prisma, …), NOT by
  replaying the full migration history — old migration chains are often broken when run from
  scratch. Guard the load so it only runs on an empty database and never wipes data on a
  container restart, and never auto-run pending migrations at startup.
• Reuse the existing Dockerfile/docker-compose.yml if present.
• Use official base images only.
• Keep images SLIM — builds run on a PM's laptop and network. Do not apt-get compiler
  toolchains or large packages (chromium, g++, libvips-dev, …) unless the app provably
  needs them: modern npm packages ship prebuilt binaries (sharp needs no libvips build,
  puppeteer downloads its own chromium). If a truly heavy native dependency is required,
  pick an official base image that already contains it instead of installing via apt.
• Do not overwrite existing files without creating a .bak backup first. CLAUDE.md is the
  exception in one direction only: replace what is between the mvpfy markers, never the
  rest of the file, and never back it up.
• Add mvpfy's own files to .gitignore if they are not already there — mvpfy.yml,
  docker-compose.mvpfy.yml, .env.mvpfy.example, .env, mvpfy-*.md, mvpfy-*.json and mvpfy/.
  They are scaffolding, and a story's pull request should never contain them. CLAUDE.md is
  NOT ignored: it is useful to whoever works on this repo next.
• Everything you generate must live under the repo root (use mvpfy/ for mock services).

Finish by writing mvpfy-run.md: which services run, their ports, how the product manager can
tell the app is working (what they should see at http://localhost:{basePort}), and any manual
steps that remain.
