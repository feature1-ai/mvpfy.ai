You are not starting from nothing. mvpfy set this app up to run locally and wrote down what
it did — read these first, they are the most reliable source of what is real and what is not:

• {bootstrapFile} — the setup task list. Any task describing a STAND-IN, a mock, a fake or a
  disabled feature is a launch finding: that part of the product is not real.
• mvpfy.yml — the run config. A `demo_login:` or `demo_credentials:` block means anyone who
  finds the app can sign in as that user.
• .env.mvpfy.example and the live env file — every setting the product needs. Values that are
  local defaults, empty, or obviously throwaway are not production values.
• docker-compose.mvpfy.yml — where the data actually lives, and whether it survives a restart.
• mvpfy-run.md — anything recorded as mocked, disabled or manual.

Then read the application code itself and look for what those files cannot tell you.

WHAT TO LOOK FOR (these are the areas; report only what you actually find evidence for):

• fake — parts of the product that are pretend: mock services, hardcoded sample responses,
  seeded fake records that would appear to real users, payments in test mode, emails that go
  to a local inbox instead of the customer.
• data — where real customer data would live and whether it survives: an ephemeral or
  file-based database, no migrations, no backup, seed/demo rows in the same database, a
  database that starts empty on every deploy.
• secrets — throwaway values that must become real (API keys, signing/session secrets, admin
  passwords), and — more seriously — any real secret committed into the repository.
• access — who can get in: a demo login that still works, authentication disabled or bypassed
  in a dev branch of the code, debug mode on, wide-open CORS, an admin page with no auth, no
  rate limiting on anything a stranger can call.
• money — anything that can cost or lose money: payment flows that are not real, no limit on
  a paid third-party API, unbounded background work.
• missing — features switched off to make local running possible, which real users would
  expect to work.
• operations — what happens when it breaks: no health check, no error tracking, no way to see
  logs, no way to roll back.

SEVERITY — be strict and honest, this is the whole value of the report:

• "blocker" — going live like this means real people LOSE MONEY, LOSE DATA, or GET ACCESS TO
  SOMETHING THEY SHOULD NOT. A live demo login, a committed secret, a database that wipes on
  deploy, a checkout that takes money into a mock. Never soften one of these.
• "risk" — it will hurt, but later rather than on day one.
• "note" — worth knowing before launch.

Do not pad the report. A short, true list beats a long, hedged one. If the product genuinely
looks ready in an area, say nothing about that area.

Write {readinessFile} — and nothing else — as JSON in exactly this shape:

Rules for the report:

• Write for the person who built the product, not for an engineer. Say what it MEANS.
    good: "Anyone can sign in as the demo account" / "The demo email and password from local
           testing still work, so anyone who finds your site can log in as a full user and see
           every customer's data."
    bad:  "Insecure default credentials present in configuration"
• Every finding needs real evidence: the file, and the line or setting that shows it. No
  finding you cannot point at.
• "fix" is what must change, not how to code it — the next step turns these into work.
• Do NOT write a verdict, a score, a summary of how ready the product is, or an "accepted"
  field. mvpfy works the verdict out from your findings, and only the builder decides what
  they are willing to launch with.

Write the file and stop.
